# Shake-the-model report — SmartSchedule

## 1. Metric under test

**Rentowność portfela** — *"marża / % projektów dowiezionych z zyskiem"* (portfolio
profitability — margin / share of projects delivered at a profit) — direction:
**up (improve = rising)**.

The metric was selected from `metryki.md` (four revenue metrics offered; this is the
headline). The requirement set below was generated by a firewalled agent that saw only
`shake-the-model-brief.md` and this metric — never the architecture — so the asks owe
nothing to the module layout and can be replayed against any alternative decomposition.

Two purely-technical components are set aside from the blast-radius measurement per the
tool's Scope rule (their whole purpose is a computational guarantee, not extensible
business behavior): the **knapsack-style optimizer** (`optimization`) and the
**dependency-ordering / parallelization solver** (`sorter`). Business modules that call
them are still counted.

## 2. Requirement set (frozen at the Step 2 gate)

Grounding for each ask is in `shake-the-model-brief.md`.

**R1 · Premium pricing for contested capabilities and windows.** When many projects
want the same skill or machine in the same window, charge more for committing that
scarce capability there; price the most sought-after capabilities and busiest windows
above the ordinary rate, leaving quiet capabilities and slack windows at standard price.
- *Mechanism on the metric:* the same finite hours are sold for more → margin per
  project rises; the premium pushes low-value work off the most-contested capacity.
- *Grounding:* "the pricing of that matching for profit"; "every commitment ties up
  capacity some other project wanted."

**R2 · A profitability bar at the door.** Before accepting a project, require it to
clear a minimum expected-margin threshold; projects that fail are declined or sent back
to renegotiate before any resource is pledged.
- *Mechanism on the metric:* loss-making work never enters the portfolio → share
  delivered at a profit rises mechanically; no scarce capacity burned on doomed work.
- *Grounding:* "abandon a project that no longer promises a profit — ideally before it
  starts"; "killing a project … most valuable before the project starts."

**R3 · Prove-then-invest discipline for growing the pool.** Every decision to buy a
machine or train a skill must be justified by a demonstrated positive payback in
advance, then held to that forecast afterward; capabilities that don't earn back their
cost get unwound, redeployed, or not repeated.
- *Mechanism on the metric:* spend steered only to capabilities that raise profitable
  output; wasted investment avoided → margin widens.
- *Grounding:* "wants a positive return on each such investment, judged forecast
  against outcome."

**R4 · Turn idle, perishable hours into paid work.** Actively drive down paid-for
resource-time that sits empty — match free windows of people and machines to project
needs still going unmet, so fewer bought-and-paid hours expire unsold.
- *Mechanism on the metric:* each idle hour converted to earning work adds revenue
  against a cost already carried and spreads standing cost across more billable output
  → margin up.
- *Grounding:* "an hour of a person or machine not sold is lost for good"; free hours
  and unmet demands coexist.

**R5 · Shield deadlines that carry penalties.** Give critical stages and projects
heading toward a penalised deadline first claim on the resources they need, ahead of
ordinary work, so penalty-bearing deliveries are protected before they slip.
- *Mechanism on the metric:* a penalty avoided is money made; a penalty incurred can
  flip a profitable delivery into a loss → protects booked margin, more projects close
  in profit.
- *Grounding:* "a late or failed delivery can carry a contractual penalty"; "watches
  for a critical stage coming up without the pieces in place."

## 3. Per-requirement impact

### R1 · Premium pricing — `classification: distributed`, `modules: 2`
**Why:** no pricing rate exists in the model today — money is captured only as a
*supplied* income/cost lump per project, decoupled from which capability or window was
committed. So a contention-sensitive rate is a new capability (CashFlow gains it), and
the contention signal plus its point of application live on the commitment side
(Allocation extends). Availability and Simulation supply the inputs unchanged. Stays at
2 only because contention data and a priced-capability what-if already exist to be
*used*; widens to a new module if the business wants a full rate-card / pricing-rules
engine rather than a rule hung on earnings.
- **CashFlow — gains:** a rate keyed to capability / window / contention; today only
  `addIncomeAndCost` records a supplied lump and `find`/`findAllEarnings` read it back.
  `doc: modules.md — allocation.cashflow`
- **Allocation — extends:** surface a per-capability-window contention measure (holds
  cross-project demands via `findAllProjectsAllocations`, exposes only summaries) and
  apply the premium at `allocateToProject`. `doc: modules.md — allocation`;
  `map: context-map.md R16`
- *uses* — **Availability** (`loadCalendars`/`findGrouped` already expose who holds each
  segment) `doc: modules.md — availability`; **Simulation** (`profitAfterBuyingNewCapability`
  already reasons over a priced capability) `doc: modules.md — simulation`.

### R2 · Profitability bar at intake — `classification: distributed`, `modules: 2`
**Why:** the new behavior is an accept/decline decision at project intake plus the
margin estimate that feeds it. The decision has a clear single home (project acceptance)
but the estimate is framed differently from any existing what-if, so two modules move.
Narrows to localized (Planning only) if the existing portfolio what-if is accepted as
the intake estimate as-is; widens if the bar must reconcile against recorded
earnings/cost definitions (CashFlow).
- **Planning — gains:** an accept / decline / renegotiate gate; `addNewProject` creates
  a project unconditionally today, with no threshold or decline path.
  `doc: modules.md — planning: addNewProject`
- **Simulation — extends:** score a *single candidate project's* expected intake margin;
  `whatIsTheOptimalSetup` / `profitAfterBuyingNewCapability` are framed around a
  capacity/portfolio optimum, not a standalone per-project intake number.
  `doc: modules.md — simulation`
- *uses* — **CashFlow** supplies the margin definition (earnings vs cost), no change if
  the forecast is Simulation's. `doc: modules.md — allocation.cashflow`

### R3 · Prove-then-invest — `classification: new-module`, `modules: 1 new + 1`
**Why:** the ask splits cleanly. "Prove before invest" is composition-only — the payback
forecast already exists. "Hold to forecast afterward" needs to persist a forecast and
reconcile it against a capability's *realized* earnings over time, and no module can host
that: the what-if engine is stateless, the resource catalog sees no money, and earnings
are attributed per project, not per capability. That missing capability forces a new
module; CashFlow must also change to make realized earnings attributable per capability.
- *uses (composition-only)* — **Simulation:** `profitAfterBuyingNewCapability` returns
  "optimal-with − price − optimal-without" — the payback forecast — as-is.
  `doc: modules.md — simulation`
- **new investment / payback ledger — gains:** persist each investment's forecast and
  reconcile against realized per-capability earnings; emit unwind/redeploy signals.
  `assumption: no module offers investment tracking or per-capability realized profit`
- **CashFlow — extends:** attribute realized earnings to the capability that produced
  them; today `find`/`findAllEarnings` are per project. `doc: modules.md — allocation.cashflow`
- *uses* — **Allocation** (which capability served which project, `findAllProjectsAllocations`)
  `doc: modules.md — allocation`; **Resource** (`scheduleCapabilities`) `doc: modules.md — resource`.

### R4 · Turn idle hours into paid work — `classification: localized`, `modules: 1`
**Why:** every primitive the ask needs already exists — read free matching capabilities,
read still-unmet demands across projects, commit a match — and a package-private matcher
already "picks any capability matching a Capability for a slot." What is missing is a
portfolio-wide driver that batches those primitives to minimize idle hours, and its
natural host is the module that already holds demands-vs-allocations and does the
committing. Nothing else changes; stays localized because the matching and commit blocks
are reused wholesale. Widens only if utilization must be *optimized* under constraints
(then the optimizer engine is invoked — used, and excluded as technical).
- **Allocation — gains:** a "match free capacity to unmet demands across the portfolio
  and commit the matches" pass; today `allocateCapabilityToProjectForPeriod` is a
  single-shot internal call and `findAllProjectsAllocations` surfaces the unmet side.
  `doc: modules.md — allocation`
- *uses* — **Availability** / **capability-scheduling** (`findAvailableCapabilities`
  returns free matching capabilities) `doc: modules.md — allocation.capabilityscheduling, availability`.

### R5 · Shield penalty-bearing deadlines — `classification: distributed`, `modules: 4`
**Why:** the ask introduces a concept the model does not have (penalty exposure) and a
rule the model does not apply (priority in contention), and both touch the full path from
project definition through contention resolution to commitment, plus the watcher that
would trigger the shield. Four modules move because no single module owns "who wins a
contested slot" end to end. It cannot stay narrower: the penalty attribute, the
priority-aware contention rule, the preemption at commit, and the proactive trigger each
live in a different module today.
- **Planning — gains:** a penalty-exposure / penalised-deadline attribute on projects and
  critical stages; it owns deadlines (`defineStartDate`) and critical stages
  (`planCriticalStage[WithResource]`) but carries no penalty concept. `doc: modules.md — planning`
- **Availability — extends:** contention resolution must honor a priority/penalty rank;
  `block` is first-come and `disable` a forcible take-over, neither keyed to desert.
  `doc: modules.md — availability: block/disable`
- **Allocation — extends:** commit penalty-exposed/critical demands ahead of ordinary
  work and preempt lower-priority commitments (`releaseFromProject` + re-allocate);
  `allocateToProject` is order-agnostic. `doc: modules.md — allocation`
- **Risk — extends:** turn "critical stage coming up without the pieces in place" into a
  proactive priority claim. `doc: modules.md — risk`; `map: context-map.md R7–R10`
- *uses* — **capability-scheduling** (`findAvailableCapabilities`); **CashFlow** (penalty
  value → margin). `doc: modules.md — allocation.capabilityscheduling, allocation.cashflow`

## 4. Aggregate over the metric

Per module, across the whole set (business modules only; `optimization` and `sorter`
excluded as technical, and are only ever *used*, never changed):

| Module | # requirements that change it | What accumulates here |
|---|---|---|
| **Allocation** | 3 (R1, R4, R5) | contention-pricing surface + apply-at-commit (R1); portfolio idle-fill driver (R4); priority commit + preemption (R5). The hub absorbs the most push on this metric. |
| **CashFlow** | 2 (R1, R3) | a capability/window/contention rate (R1); per-capability realized-earnings attribution (R3). Money-shaping asks concentrate here. |
| **Planning** | 2 (R2, R5) | an intake accept/decline gate (R2); a penalty-deadline attribute (R5). |
| **Simulation** | 1 (R2) | a per-candidate intake-margin readout (R2). Its payback what-if is reused unchanged by R3. |
| **Availability** | 1 (R5) | priority/penalty-aware contention resolution (R5). Reused unchanged by R1 and R4. |
| **Risk** | 1 (R5) | proactive shield trigger off its critical-stage watch (R5). |
| **new investment/payback ledger** | 1 (R3) | the only capability with no existing home: forecast persistence + realized-payback reconciliation. |
| **Resource** | 0 | only *used* (R3), never changed. |

Which modules absorb the business's push on portfolio profitability: **Allocation**
(three of five asks), then **CashFlow** and **Planning** (two each). Which never feel it:
**Resource**, and the two technical engines.

## 5. Distribution

`localized: 1` (R4) · `distributed: 3` (R1, R2, R5) · `new-module: 1` (R3).

Spread of the distributed asks: R1 = 2 modules, R2 = 2 modules, R5 = 4 modules (crosses
the project-definition, contention, commitment, and risk boundaries). R3 forces one new
module and changes one existing (CashFlow).

## Replay note

This requirement set derives only from `shake-the-model-brief.md` and the metric above —
never from this architecture. To compare an alternative decomposition of the same
business, keep the five asks frozen, establish the other model's module + capability
inventory, and rerun Step 3 against it. Same asks, different model; the per-requirement
classifications, the aggregate, and the distribution are then directly comparable, and
any difference is attributable to the models alone.
